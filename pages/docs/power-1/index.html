Version distinction: POWER 1.0 is a browser-side templating and SPA routing experiment. POWER 2.0 is a separate Node.js web framework. Their architecture and setup instructions are not interchangeable.

01. Overview & architecture

POWER stands for Page Observer with Extraction & Route. It uses native browser APIs rather than a virtual DOM or third-party router. The runtime fetches HTML files, converts their nodes into document fragments, prepares route data, and renders the selected page inside one root element.

main.js
  → new App()
  → App.Run()
  → TemplateBuilder(routes)
  → IdentifyInlineCommands(pages)
  → Route()
  → LoadRequestedPage()
  → props → page scripts → DOM

Core browser APIs include fetch(), Map, DocumentFragment, history.pushState(), popstate, TreeWalker, Blob, and URL.createObjectURL().

02. Setup & entry point

The demo entry point main.js imports App from App.js, configures a root element and route table, then calls app.Run(). Serve the files over HTTP because templates and scripts are loaded with fetch(); opening via file:// may fail.

import App from "./App.js";

const app = new App({
  root: document.getElementById("app"),
  routes: {
    home: {
      href: "/",
      path: "./pages/home.html",
      props: { msg: "Welcome to Power Engine" }
    },
    about: {
      href: "/about",
      path: "./pages/about.html"
    },
    "404": {
      href: "/404",
      path: "./pages/notfound.html"
    }
  },
  authenticate: {}
});

app.Run();

For a quick local static server, run python -m http.server 8000 from the project directory, then open http://localhost:8000.

03. Routes & navigation

Each route requires string fields href and path, with optional object-valued props. The runtime delegates clicks from elements marked with data-meta-href, prevents normal navigation, and loads the matching route. It also listens for popstate to support browser Back and Forward.

<a data-meta-href="/">Home</a>
<a data-meta-href="/about">About</a>
<button data-meta-href="/demo-page">Open demo</button>

NormalizeRoute() normalizes route identifiers; NormalizeFilePath() separately normalizes resource paths.

04. Template loading & cache

TemplateBuilder(routes) validates route definitions, fetches each HTML file through GetHtml(), converts its nodes into a DocumentFragment, and stores the fragment plus optional props in a Map. Rendering clones the cached fragment so the prepared template remains available for later navigation.

pages.set("/about", {
  fragment: DocumentFragment,
  props: { title: "About" }
});

05. Props interpolation

PropsUpdater(page) clones a page fragment and replaces placeholders in text nodes and element attributes. Nested paths such as user.name are supported; missing values become empty strings.

// Route props: { user: { name: "Alex" }, title: "Welcome" }

// Template:
<h1>{{ title }}</h1>
<p>Hello, {{ user.name }}</p>
<img src="{{ avatarUrl }}" alt="Profile">

{{ value }} is ordinary interpolation; {{{ value }}} inserts raw HTML. The implementation also parses interpolated text containing a less-than character as HTML, so double braces are not a reliable HTML-escaping boundary.

Security note: Never insert untrusted values through triple braces. Sanitize or explicitly escape user-controlled content before rendering; the current implementation can expose HTML injection / XSS risks.

06. HTML & CSS includes

Use an include element to load reusable markup or a stylesheet. HTML includes are processed recursively, allowing nested components. Both type and path are required.

<include type="html" path="./components/navbar.html"></include>

<include type="css" path="./styles/main.css"></include>

Implementation note: CSS duplicate detection compares an absolute link URL with a normalized path string, which may not match. Test repeated CSS includes and consider comparing resolved URLs.

07. Page-scoped scripts

FindScriptsAndModuleThem() collects script elements from a rendered fragment. Inline code is wrapped in an immediately invoked function; external files are fetched using a path based on App.BASE_PATH. Code is placed in a Blob, exposed through an object URL, and attached as a script for the current page.

<script>
  console.log("Page rendered");
</script>

<script src="./pages/demo.js"></script>

This is lifecycle organization, not a security sandbox. Verify resource paths when hosting below a domain root and review cleanup during repeated navigation.

08. Render lifecycle & 404

LoadRequestedPage(key, root, pages) looks up the route or falls back to the configured /404 page, updates browser history, clones the fragment, applies props, extracts scripts, clears the root, inserts the new page, then executes its scripts. The fallback only works if a /404 route is defined.

Requested route
  → route or /404
  → update history
  → clone fragment
  → apply props
  → collect scripts
  → render page
  → execute page scripts

09. Core App API

new App({ root, routes, authenticate })

Stores configuration; root defaults to document.body.

Run()

Validates configuration, prepares templates and includes, and starts routing.

TemplateBuilder()

Loads and prepares route templates.

GetHtml()

Fetches an HTML template from its configured path.

PropsUpdater()

Injects route-specific values into text and attributes.

LoadIncludeCommands()

Expands reusable HTML and CSS includes.

Route()

Handles delegated navigation and browser history events.

LoadRequestedPage()

Renders the requested route or configured fallback.

The authenticate option is a placeholder; the source does not implement a complete authentication system.

10. Security & limitations

  • The README describes POWER Engine as experimental / educational, not hardened for production.
  • HTML interpolation is not safely escaped in all code paths; untrusted values can create XSS risk.
  • Authentication, authorization, route guards, and dynamic route parameters are not implemented in the documented source.
  • Page scripts use object URLs; review resource cleanup and behavior during repeated navigation.
  • Test deployment under subpaths, failed fetches, browser Back/Forward, nested includes, and the configured 404 route.
Recommended use: Treat POWER 1.0 as a learning project or prototype. Review the source and address security gaps before exposing applications to untrusted input.
